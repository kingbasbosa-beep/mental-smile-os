# The Great Cleanup Map V1

Result: MENTAL_SMILE_HISTORY_COMPLETE

Purpose: create one master map of the Mental Smile evolution from Mental Key Era to Mental Smile OS Era.

## Executive Summary

Mental Smile did not become Mental Smile OS by renaming a project. It became Mental Smile OS by separating identity, authority, runtime, archive, discovery, public story, and infrastructure.

The historical journey moved through eight major shifts:

1. Mental Key and early app identity.
2. Marketplace/booking assumptions.
3. Admin-centered authority.
4. Clean Core as source and runtime dependency.
5. Constitutional federation.
6. Signal federation.
7. Admin Zero and Owner Authority.
8. Generation 1 Release Candidate with conditional OS-only certification.

The great cleanup did not erase history. It classified it.

## Major Decisions

| Decision Area | Old Direction | New Direction |
| --- | --- | --- |
| Product identity | Mental Key / mixed app identity | Mental Smile OS |
| Business model | booking/payment/session marketplace assumptions | discovery and support ecosystem |
| Authority | admin/admins/super-admin style power | Owner Authority + Admin Zero |
| Runtime dependency | clean core dependency | OS-owned runtime modules |
| Architecture | mixed app surface | federation of zones, gateways, signals, cards, registries |
| Public role | unclear service/app identity | Arabic-first mental health discovery and support ecosystem |
| Data movement | direct operational assumptions | signal federation and gateway routing |
| Archive | scattered historical docs | archive cards + historical knowledge registry |
| Release | validation equals readiness | Owner-governed release gate |

## Major Mistakes

1. Admin language survived after the authority model changed.
2. Booking/payment/session assumptions remained in historical planning.
3. Flutter template identity and Mental Key labels stayed too long.
4. Clean Core stayed active as dependency instead of source evidence.
5. Documentation became more complete than runtime.
6. Placeholder routes looked like product features.
7. Signal federation was defined before full signal runtime validation.
8. Release readiness was initially confused with build readiness.
9. Public explanation became clearer than the actual first-minute journey.
10. Archive evidence grew without a navigation system.

## Major Successes

1. Admin Zero doctrine replaced broad admin authority.
2. Owner Authority became the named governance path.
3. Booking/payment/session authority was removed from Generation 1 scope.
4. Provider registration was separated from provider public display.
5. Center registration was separated from center public display.
6. Clean Core was preserved as source evidence but removed as active dependency.
7. Dart package identity became `mental_smile_os`.
8. Android namespace became `com.mentalsmile.os`.
9. Archive cards turned history into structured memory.
10. OS-only certification became conditional instead of falsely declared.

Old:

- sessions

- service operations

New:

- support pathways

- center visibility
- knowledge access
- support signals

## Signal Federation Evolution

Old risk:

- Direct cross-zone dependencies.
- Tool-to-provider coupling.
- Content-to-client mutation.

New doctrine:

- Surface emits signal.
- Local gateway receives.
- Signal pipe forwards.
- Target gateway receives.
- Target zone consumes internally.

The doctrine is complete; runtime validation remains an execution task.

## Admin Zero Evolution

Old:

- admin
- admins collection fallback
- super-admin assumptions
- broad elevated access

New:

- Owner claim authority
- no god mode
- monitoring may observe but not authorize
- archive stores but does not govern
- strategic analyzes but does not execute

## Archive Evolution

Old:

New:

- engineering lessons
- educational signals
