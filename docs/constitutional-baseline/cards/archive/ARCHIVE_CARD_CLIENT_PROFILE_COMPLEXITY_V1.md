# Archive Card Client Profile Complexity V1

Status: ACTIVE_ARCHIVE_CARD
Classification: CLIENT_IDENTITY_EXTRACTION_ERA
Archive type: Client profile simplification evidence
Runtime effect: none

## Subject

Client profile complexity, client login weight, stored preferences, and persistence-heavy client identity patterns.

## Archive Reason

Client profile, login, preferences, and persistence became constitutional simplification candidates because profile-heavy identity can conflict with Mental Smile's fresh signal doctrine.

The historical pattern stored or implied too much client identity too early:

- login before value may become a heavy access gate
- profile fields may become durable assumptions
- saved preferences may become stale analytics
- registration-time selections may be treated as stable identity
- persistent profile data can outlive the context in which it was selected

This card archives the reasoning for simplification. It does not delete, migrate, or change runtime behavior.

## Evidence Value

This archive card preserves the origin of the Client Identity Extraction Era:

- why client identity became a simplification candidate
- why fresh repeated intent should outrank old stored preferences
- why stateless or lighter client rooms may be safer future doctrine
- why runtime implementation must be separately approved and verified

## Constitutional Boundary

Client simplification must not create:

- hidden tracking
- diagnosis inference
- clinical identity labels
- ungoverned personalization
- deletion without archive memory
- runtime removal without Owner approval

## Rule

Archive profile complexity before simplifying it.

Any future removal of login, profile persistence, stored preferences, or client identity fields must pass:

```text
Finding
-> Decision Card
-> Archive Card
-> Owner Approval
-> Runtime Plan
-> Implementation
-> Verification
-> Operation Registration
-> Memory Update
```
