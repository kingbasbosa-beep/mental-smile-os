# Accessibility Gateway Guide V1

Status: ACTIVE_GOVERNANCE_GUIDE
Classification: ACCESSIBILITY_GATEWAY_FOUNDATION
Phase: 7B
Runtime effect: none

## Purpose

Define the Mental Smile accessibility gateway doctrine before any runtime implementation.

Mental Smile does not classify users.

Mental Smile removes barriers.

Accessibility is access, not segregation.

## Doctrine

Accessibility is a shared access layer for the whole city. It must not create a separate class of users, a lower path, a medical label, or a hidden identity category.

The accessibility gateway exists to make the same city easier to enter, understand, and use.

## Mental Smile Does Not Classify Users

Mental Smile must not use accessibility needs as identity labels.

Allowed language:

- access need
- communication preference
- support mode
- barrier removal
- accessible contact path
- simplified content preference

Forbidden language:

- diagnostic identity
- disability classification by the platform
- permanent user label
- separate user class
- eligibility gate

## Mental Smile Removes Barriers

The accessibility gateway should reduce friction in:

- communication
- navigation
- content understanding
- video learning
- organization discovery
- AI assistant access
- visual assistance
- contact paths

Removing barriers means creating alternate access routes into the same Mental Smile experience.

## Accessibility Is Access, Not Segregation

Accessibility surfaces must not isolate people away from the main city.

An accessibility room may organize access resources, but it must point back into the same trusted city, the same support doctrine, and the same governance rules.

## Governance Boundary

This guide does not authorize:

- runtime routes
- Firebase collections
- user labels
- diagnosis fields
- medical claims
- organization verification
- AI behavior changes

Any future implementation requires Owner approval, validation, and operation registration.
