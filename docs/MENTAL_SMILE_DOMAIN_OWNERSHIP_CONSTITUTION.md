# MENTAL SMILE DOMAIN OWNERSHIP CONSTITUTION

هذه الوثيقة هي المرجعية المعمارية الرسمية لملكية الدومينات داخل Mental Smile.

الغرض منها تثبيت أن:

```text
Mental Smile = سوق خدمات الصحة النفسية
```

وليس منصة علاج، ولا نظام حجز مركزي، ولا وسيط دفع، ولا نظام محاسبي، ولا جهة اعتماد رسمية، ولا Super Admin Platform.

---

# 1. Core Identity

Mental Smile هو **سوق خدمات الصحة النفسية**.

وظيفته الأساسية:

* عرض مقدمي الخدمة
* تسهيل وصول العميل للخدمة
* دعم ووقاية وتعليم
* شفافية وثقة
* تقييمات وتعليقات
* شكاوى وروابط تحقق
* تمكين الأخصائيين والمراكز
* تسويق وخدمات مهنية

Mental Smile ليس:

* مقدم علاج
* جهة تشخيص
* وسيط مالي
* محصل أموال جلسات
* نظام محاسبي مركزي
* جهة اعتماد أو ترخيص حكومية
* نظام Booking مركزي

المبدأ الحاكم:

```text
Marketplace
+
Trust Through Transparency
+
Support
+
Education
+
Professional Enablement
```

Mental Smile لا يملك علاقة الرعاية نفسها. علاقة الرعاية، التشخيص، العلاج، الدفع، والالتزام المهني تظل بين العميل ومقدم الخدمة، تحت إفصاح واضح.

---

# 2. Core Domains

## Marketplace Domain

يمتلك:

* provider discovery
* clinician profiles
* center profiles
* services display
* provider-declared prices
* comparison
* public visibility

لا يمتلك:

* payment
* payout
* accounting
* treatment
* diagnosis
* booking as core dependency

هذا الدومين مسؤول عن إظهار السوق نفسه: مين مقدم الخدمة، فين، بيقدم إيه، بأسعار معلنة من مقدم الخدمة، وبأي معلومات عامة تساعد العميل يقارن ويفهم.

## Trust & Transparency Domain

يمتلك:

* provider submitted credentials
* licenses
* disclosed documents
* verification sources
* complaint visibility
* ratings
* comments
* transparency history

الفلسفة:

```text
Trust by Transparency, not Trust by Platform Guarantee.
```

Mental Smile لا تضمن النتيجة، ولا تضمن جودة العلاج، ولا تعلن اعتماد رسمي من الدولة. المنصة تعرض البيانات التي قدمها مقدم الخدمة، تعرض وسائل التحقق، تعرض التقييمات والتعليقات والشكاوى، وتعرض تاريخ الشفافية.

لا تظهر أي صيغة توحي بضمان أو اعتماد رسمي إلا في حالة خدمة تحقق اختيارية منفصلة وبسياسة واضحة.

## Client Support Domain

يمتلك:

* support
* prevention
* education
* library access
* complaint links
* hotlines
* non-clinical guidance

هذا الدومين يساعد العميل يفهم، يوصل، يتعلم، ويبلغ عن مشكلة. لكنه لا يشخص، ولا يعالج، ولا يقدم خطة علاج شخصية.

## Education & Library Domain

يمتلك:

* articles
* exercises
* videos
* audio
* prevention content
* family support content
* addiction education
* special needs support content
* multilingual future content

لا يقدم:

* diagnosis
* therapy
* personalized treatment plan

كل محتوى المكتبة تعليمي ووقائي وداعم. لا يتم تقديمه كبديل لطبيب أو أخصائي أو خطة علاج.

## Professional Enablement Domain

يمتلك:

* professional tools
* AI assistant
* reports
* content creation
* marketing tools
* digital clinic tools
* optional CRM integrations
* paid resources

هذا الدومين مسؤول عن تمكين الأخصائي أو مقدم الخدمة مهنيًا وتسويقيًا وتشغيليًا، بدون تحويل المنصة إلى مالك للجلسة أو العلاقة العلاجية.

## Center Enablement Domain

يمتلك:

* center profile
* services
* prices as disclosure
* licenses as disclosure
* marketing/content
* future courses/diplomas hooks
* rented service spaces

المركز مسؤول عن صحة بياناته، خدماته، أسعاره، وثائقه، سياساته، وردوده على الشكاوى. Mental Smile يعرض ويدعم الشفافية، لكنه لا يصبح المركز ولا يدير التزاماته المالية أو العلاجية.

# 3. Optional Capability Modules

```text
Optional Modules are NOT Core Dependencies.
```

أي Optional Module ممكن يتفعل، يتأجر، يتفصل، أو يتقفل. لو أي module اتقفل أو اتفصل، Core Mental Smile يجب أن يظل يعمل.

## Booking Module

* optional
* rentable
* tenant-scoped
* not core
* does not own Mental Smile marketplace

الـ Booking يخدم طلب موعد أو تنسيق ميعاد أو availability، لكنه لا يملك السوق ولا يصبح شرطًا لعمل المنصة.

## Accounting Module

* optional
* for center/professional internal use
* not used by Mental Smile core
* no platform commission logic

المحاسبة تخص المركز أو الأخصائي داخليًا. Mental Smile core لا يبني دخله على عمولة جلسة ولا يدير payout أو تحصيل مركزي.

## CRM Module

* optional
* provider-owned client management
* tenant-scoped

الـ CRM لو موجود فهو أداة لمقدم الخدمة، وليس سجل ملكية مركزي لكل علاقة بين عميل ومقدم خدمة.

## Verification Service

* optional premium trust service
* may produce `Verified by Mental Smile` badge
* not required for all providers
* does not turn Mental Smile into government licensing authority

خدمة التحقق تضيف طبقة ثقة اختيارية مدفوعة أو مميزة، لكنها لا تجعل Mental Smile جهة ترخيص حكومية أو جهة اعتماد عامة لكل السوق.

## Academy Module

* optional
* courses/diplomas/training spaces

هذا الموديول يسمح بمساحات تعليمية وتدريبية مستقبلية، خصوصًا للمراكز أو الجهات التي تقدم كورسات أو دبلومات أو تدريبات.

## Marketing Suite

* optional
* content/campaign/promotion tools

هذا الموديول يدعم صناعة المحتوى والحملات والظهور والترويج، بدون خلطه مع العلاج أو الدفع أو الحجز كـ Core.

## AI / Translation Suite

* optional
* multilingual support
* translation
* content tools
* professional productivity

هذا الموديول يدعم الإنتاجية والترجمة والمحتوى والدعم متعدد اللغات مستقبلًا، ولا يقدم تشخيصًا أو علاجًا أو ضمانًا علاجيًا.

# 4. Trust Doctrine

## Core Trust Layer

يعتمد على:

* الإفصاح
* عرض الوثائق
* عرض مصادر التحقق
* التقييمات
* التعليقات
* الشكاوى
* السجل العام للشفافية

Core Trust Layer هو طبقة عرض وشفافية. المنصة تقول: هذه بيانات مقدم الخدمة، هذه الوثائق التي أفصح عنها، هذه مصادر التحقق المتاحة، هذه التقييمات، هذه التعليقات، وهذه الشكاوى أو الردود المسجلة.

## Verification Service

Verification Service خدمة اختيارية فقط.

لا تظهر عبارة `Verified by Mental Smile` إلا لو:

* provider طلب خدمة تحقق
* تمت مراجعة الوثائق وفق policy محددة
* تم تسجيل review record
* badge له تاريخ صلاحية أو review cycle

أي badge يجب أن يكون له معنى محدود وواضح: تم تنفيذ مراجعة وفق سياسة محددة. لا يعني ضمان جودة العلاج، ولا اعتماد حكومي، ولا ضمان صحة كل شيء للأبد.

---

# 5. No Cross-Domain Collections Doctrine

القانون:

```text
No collection may own multiple domains.
```

المشكلة ليست اسم `booking_requests` فقط.

المشكلة كانت أن collection واحدة حملت:

* request
* booking
* payment
* payout
* accounting
* review
* archive
* reports

وهذا ممنوع تكراره.

حتى لو تم إنشاء `service_requests` مستقبلًا، لا يجوز أن تتحول إلى مهلّبية جديدة تجمع كل شيء تحت اسم أهدى.

كل Domain يجب أن يكون له:

* collections
* routes
* roles
* rules
* reports
* policies
* archive behavior

أي collection جديدة يجب أن يكون لها owner واضح، وحدود واضحة، وما لا تملكه يكون مكتوبًا قبل التنفيذ.

---

# 6. Booking Request Doctrine

`booking_requests` الحالية تصنف كالتالي:

```text
Frozen + Quarantined + Legacy Candidate
```

الـ Booking ليس Core Domain.

الـ Booking هو:

```text
Optional Capability Module
```

ممنوع:

* بناء core platform جديد فوق `booking_requests`
* توسيعها
* إضافة payment/accounting/payout لها
* اعتبارها قلب المنصة

مستقبلها يتحدد لاحقًا:

* transform into module
* migrate to module
* bury as legacy

إلى أن يتم اتخاذ قرار رسمي، يتم التعامل مع `booking_requests` كمنطقة مجمدة ومعزولة. أي تعديل عليها يحتاج مبرر واضح، تصنيف دومين، واختبار حدود.

# 7. Platform Responsibility Model

Mental Smile مسؤولة عن:

* الوصول للخدمة
* الشفافية
* الدعم
* التعليم
* الوقاية
* التقييمات
* التعليقات
* الشكاوى
* عرض التراخيص والبيانات
* تمكين مقدمي الخدمة

Mental Smile غير مسؤولة عن:

* نتيجة علاج
* تشخيص
* خطة علاج
* دفع الجلسات
* تحصيل
* عمولات
* Payout
* Accounting
* النزاعات المالية المباشرة بين العميل ومقدم الخدمة

المنصة تقدر تساعد في البلاغ، الشفافية، عرض السجل، وروابط الشكاوى. لكنها لا تتحول لطرف مالي أو طبي داخل علاقة الرعاية.

---

# 8. Rules and Routes Doctrine

أي Route أو Rule أو Collection يجب أن يصنف إلى واحد من:

* Core
* Control
* Optional Module
* Legacy
* Quarantined
* Burial Candidate

لا يتم تعديل Firestore rules إلا بعد:

* Domain ownership clarity
* Route classification
* Tests
* Owner approval

أي route جديد لازم يجاوب على سؤال بسيط قبل التنفيذ: هو تابع لأي domain؟ هل هو Core؟ Control؟ Optional Module؟ Legacy؟ Quarantined؟ أم Burial Candidate؟

أي rule جديدة لازم تكون انعكاسًا لملكية الدومين، وليس محاولة لسد فجوة تصميمية ناتجة عن collection تحمل أكثر من مسؤولية.

---

# 9. Final Constitutional Verdict

```text
Mental Smile is a Mental Health Services Marketplace.

It does not own the care relationship.

It enables access, transparency, support, education, and professional growth.

Optional modules may be rented, hosted, or activated, but they must never become hidden dependencies of the core platform.
```
