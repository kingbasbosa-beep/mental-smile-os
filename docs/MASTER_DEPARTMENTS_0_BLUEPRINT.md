# Mental Smile Department Blueprint

Status: Department/function blueprint  
Runtime effect: None  
Implementation effect: None  
Date: 2026-05-30

This document defines Mental Smile departments as operational entities.

It is not implementation.
It is not runtime.
It is not a staffing plan.
It does not change routes, Firestore, rules, code, or legacy surfaces.

It defines responsibilities, authority, inputs, outputs, reports, escalation paths, archive obligations, and activation maturity.

---

# PART A: Department Doctrine

## A1. Core Doctrine

```text
Department
!=
Person

Department
=
Operational Function
```

A department is a repeatable responsibility area with defined inputs, outputs, authority limits, reports, escalation paths, and archive duties.

A person may temporarily hold a department function. That does not mean the department is mature. It means the function has a delegated holder.

## A2. Department Purpose

Departments exist to prevent invisible authority and chaotic decision-making.

Each department answers:

- What signals does this function receive?
- What decisions can it recommend?
- What can it execute without Owner ratification?
- What must it escalate?
- What reports does it produce?
- What must it archive?
- What maturity level does it currently have?

## A3. Delegated Function Concept

A delegated function is a department responsibility held temporarily before a mature department exists.

Delegated functions must have:

- scope
- limits
- report duties
- archive duties
- escalation path
- review cycle

Delegation is not permanent authority transfer.

```text
Delegation is a bridge.
It is not a throne.
```

## A4. Activation Maturity Concept

Department maturity levels:

| Level | Name | Meaning |
|---|---|---|
| Level 0 | Concept | Exists as doctrine/category only. |
| Level 1 | Delegated | Function has a temporary holder/process. |
| Level 2 | Operational | Function performs repeatable work with reports. |
| Level 3 | Governed | Function has reviewed authority, archive, and boundaries. |
| Level 4 | Enforced | Function has hard runtime/process enforcement and protected memory where needed. |

Hard enforcement should not appear before Level 3.

## A5. Future Staffing Concept

Staffing may come later. Staffing must follow function maturity, not create fake maturity.

A staffed department should exist only when there is:

- enough recurring work
- clear scope
- review process
- archive process
- accountability
- authority boundaries
- escalation paths

# PART B: Owner Room Blueprint

## Purpose

The Owner Room preserves constitutional legitimacy and ratifies high-risk, strategic, cross-domain, or policy-changing decisions.

## Responsibilities

- constitutional leadership
- strategic direction
- final ratification where required
- delegation approval and review
- high-risk trust/legal/finance/policy decisions
- cross-department conflict resolution
- quarterly governance acceptance
- department activation decisions
- authority boundary protection

## Inputs

- department recommendations
- Control reports
- trust appeals/exceptions
- quarterly governance packages
- technical risk recommendations
- legal/rights concerns
- finance/legal frozen-domain signals
- archive summaries
- pilot readiness reports

## Outputs

- ratified decisions
- accepted/deferred/rejected recommendations
- delegation approvals
- department activation decisions
- strategic direction
- constitutional amendments or amendment candidates
- action package approval

## Reports Received

- operational incident reports
- verification backlog and exception reports
- support continuity reports
- survey analysis packages
- technical reports
- content/library reports
- finance/legal freezer reports
- quarterly governance package
- archive package index

## Ratification Authority

Owner ratification is required for:

- constitutional decisions
- strategic direction
- high-risk trust actions
- appeal outcomes with precedent risk
- finance/legal policy
- user rights or consent changes
- authority boundary changes
- department activation
- cross-domain conflicts

## Delegation Authority

The Owner may delegate functions temporarily. Each delegation must define scope, limits, review date, and archive duties.

## Quarterly Governance Role

The Owner:

- receives quarterly package
- reviews department reports
- accepts or rejects recommendations
- renews or ends delegations
- identifies frozen debt
- confirms next action packages

## Archive Obligations

Archive:

- ratification notes
- decisions accepted/rejected/deferred
- delegation records
- department activation decisions
- constitutional amendments
- quarterly acceptance notes

## Current Maturity

Level 1 Delegated.

Owner leadership exists, but the formal Owner Room process is not mature.

## Future Maturity

Level 3-4 once ratification records, delegation cycles, quarterly governance, and protected memory are repeatable.

# PART D: Trust Function Blueprint

## Purpose

Trust verifies whether clinicians and centers may safely participate, appear, operate, or continue in Mental Smile workflows.

## Responsibilities

- clinician verification
- center verification
- identity/document/license review
- known-partner exception review
- unknown-applicant review
- profile change review
- appeal handling
- suspension/reactivation recommendation
- trust records
- verification backlog reporting

## Inputs

- clinician registration
- center registration
- profile change requests
- identity/licensing documents or references
- known-partner context
- complaints
- support risk signals
- legal/rights concerns
- resubmissions
- appeals

## Outputs

- approved / rejected / needs review / suspended recommendations
- clarification requests
- trust decision notes
- appeal outcome recommendation
- reactivation recommendation
- verification backlog report
- TRUST_VERIFICATION_RECORD

## Verification Duties

Trust reviews:

- identity
- contactability
- license or registration evidence
- specialty or service fit
- affiliation
- location for centers
- responsible person for centers
- public presence where useful
- missing/expired/conflicting evidence

## Appeals

Appeals require:

- original decision review
- new evidence review
- fairness check
- Owner involvement where high-risk, contested, or precedent-setting
- archive package

## Suspensions

Suspension is considered when:

- complaint creates trust risk
- evidence becomes invalid
- document contradiction appears
- legal/safety issue appears
- participation risk changes

Suspension should define scope, reason, review date, and reactivation conditions.

## Reactivations

Reactivation requires:

- blocker resolved
- evidence reviewed
- complaint/legal hold checked
- Owner ratification if prior suspension was high-risk
- archive record

## Reports

- verification backlog
- missing evidence report
- approval/rejection summary
- known-partner exception report
- unknown-applicant risk report
- appeal report
- suspension/reactivation report

## Trust Records

Minimum record:

- entity type
- entity identity
- applicant type
- evidence reviewed
- missing evidence
- reviewer
- decision
- rationale
- date
- next review date if needed
- appeal/resubmission links

## Authority Boundaries

Trust recommends and performs review. It must not:

- become generic admin approval forever
- bypass human review
- erase evidence
- approve unknown applicants without minimum evidence
- skip archive
- become legal or finance authority

## Current Delegated Reality

Level 1 Delegated.

Trust works through admin surfaces, PF-2 checklist discipline, and manual archive.

## Future Trust Department

Future Level 3 Trust Department requires:

- clear intake
- consistent verification records
- appeal process
- suspension/reactivation process
- protected memory or audit trail
- reporting cadence
- separation from generic admin authority
