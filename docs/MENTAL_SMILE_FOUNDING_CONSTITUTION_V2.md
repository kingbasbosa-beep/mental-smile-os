# PART A: Constitutional Identity

## A1. What Mental Smile Is

Mental Smile is a constitutional operational federation under construction.

It is an operational ecosystem that may include app workflows, web workflows, support continuity, trust verification, finance, legal, content, analytics, technical systems, partnerships, tenants, clinicians, centers, clients, and future hosted environments.

Mental Smile is not merely:

- a Flutter app
- a Firebase project
- an admin panel
- a booking system
- a support workflow
- a finance workflow
- a founder-led operation

Mental Smile is an institution being constructed to govern operational truth, human support, finance/legal responsibility, and institutional memory under constitutional limits.

## A2. What Mental Smile Is Not

Mental Smile is not:

- a super-admin cockpit
- a founder monarchy
- a backend dictatorship
- an AI-governed system
- a finance/legal mutation console
- a route-renaming project
- a data-hoarding machine
- a client-device-only truth system
- a symbolic governance theater
- a governance fantasy pretending mature departments already exist

## A3. Constitutional Federation Doctrine

Mental Smile shall become constitutional through construction, not declaration.

The federation must distinguish:

- visibility from authority
- authority from mutation
- mutation from sovereignty
- leadership from execution
- delegation from ownership
- operational truth from protected memory
- AI analysis from governance

Core federation purpose:

```text
Operate usefully.
Limit power.
Protect memory.
Preserve dignity.
Grow without collapse.
```

## A4. Operational Ecosystem Doctrine

Mental Smile is an ecosystem of domains, not one room.

Its future operational ecosystem includes:

- Control Room
- Owner Room
- Governance Departments
- Technical Department
- Trust & Verification
- Finance
- Legal + HR
- Marketing & Content

- Knowledge & Archive Office

## A5. Mission Continuity

Mental Smile must survive:

- founder overload
- developer change
- hardware failure
- route migration
- team growth
- governance expansion
- technology change
- disputes
- finance/legal risk
- institutional memory pressure

Mission continuity requires:

```text
Continuity before expansion.
Memory before authority.
Construction before enforcement.
```

# PART C: Governance Topology

## C1. Official Topology

```text
SYSTEM
↓
CONTROL ROOM
↓
GOVERNANCE DEPARTMENTS
↓
OWNER ROOM
```

This topology describes flow, not personal hierarchy.

## C2. Signal Flow

Signals originate from users, runtime events, operational queues, disputes, support, verification, finance anomalies, legal concerns, content issues, and technical failures.

Signal flow:

```text
User / Runtime
-> System
-> Control Room
-> Governance Department
-> Owner Room if required
```

## C3. Information Flow

Information flows upward as facts, summaries, reports, cases, evidence, and analysis.

Information must be scoped, redacted where needed, and routed to the correct department.

## C4. Report Flow

Reports may be daily, weekly, monthly, or quarterly.

- Daily: urgent exceptions and incidents.
- Weekly: queues, verification, support, technical risk.
- Monthly: governance risks, freezer status, data/memory gaps.
- Quarterly: governance package, constitutional review, frozen debt, backup manifests, amendment candidates.

## C5. Recommendation Flow

Departments analyze signals and produce recommendations.

Recommendations must include:

- evidence
- risk
- human analysis
- AI-assisted analysis where useful
- authority requirement
- memory requirement
- proposed action

## C6. Ratification Flow

Ratification flows downward from Owner Room only where required.

Owner ratifies:

- constitutional changes
- strategic direction
- high-risk policy
- cross-department conflicts
- partnership governance
- registry/pipeline legitimacy
- broad finance/legal policy impacts

Owner does not ratify every routine operation.

## C7. Archive Flow

Archive flow captures:

- reports
- decisions
- quarterly packages
- governance reviews
- migration waves
- extraction waves
- sovereign waves
- backup manifests
- constitutional history

Archive is institutional continuity.

## C8. Delegation Flow

```text
Department Missing
-> Delegation
-> Temporary Holder
-> Review
-> Department Activation
```

Delegation must be scoped, reviewed, and temporary.

# PART I: Governance Maturity Doctrine

## I1. Level 0: Concept

The unit exists only as doctrine or category.

Activation requirement:

- definition and purpose.

Enforcement:

- none.

## I2. Level 1: Delegated

Responsibility is temporarily held by an existing person/function.

Activation requirement:

- scope, limits, review date.

Enforcement:

- documentation and warnings only.

## I3. Level 2: Operational

The unit performs regular work.

Activation requirement:

- repeated process, reports, owner visibility.

Enforcement:

- warnings and soft validation.

## I4. Level 3: Governed

The unit has boundaries, review, records, and accountability.

Activation requirement:

- reporting, archive, escalation, review.

Enforcement:

- governed execution may begin.

## I5. Level 4: Enforced

Runtime validates or blocks forbidden actions.

Activation requirement:

- mature governance
- protected memory
- command boundary
- rollback/correction process
- fallback
- testing

Enforcement:

- hard validation.

Maturity law:

```text
Hard enforcement should not appear before Level 3 maturity.
```
