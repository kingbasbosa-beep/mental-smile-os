# PART A: Governance Topology Overview

## A1. Official Constitutional Topology

Mental Smile's constitutional governance topology is:

```text
SYSTEM
↓
CONTROL ROOM
↓
GOVERNANCE DEPARTMENTS
↓
OWNER ROOM
```

This topology describes flow, not social status.

The System produces operational signals. Control Room observes and aggregates. Governance Departments analyze by domain. Owner Room ratifies constitutional, strategic, high-risk, or cross-domain decisions.

Core law:

```text
Information flows upward.
Ratification flows downward.
```

## A2. Flow Types

| Flow | Direction | Meaning |
| ---- | --------- | ------- |
| signal flow | System -> Control -> Departments -> Owner | Runtime events become governance awareness. |
| information flow | Operational surfaces -> reports -> governance package | Facts move upward for analysis. |
| escalation flow | Control -> Department -> Owner where needed | Risk or unresolved issue moves to appropriate authority. |
| recommendation flow | Department -> Owner | Domain analysis becomes proposed action. |
| ratification flow | Owner -> Department/Technical/System | Approved decision returns downward for execution. |
| archive flow | All governance units -> Knowledge & Archive Office | Decisions, reports, and history become institutional memory. |

## A3. Constitutional Meaning

The topology prevents three failures:

1. Control Room becoming super-admin.
2. Owner Room becoming daily operations.
3. Departments becoming invisible authority islands.

The topology also prevents runtime fantasy:

```text
Departments that do not exist yet may be represented by delegated functions,
but not falsely treated as mature institutions.
```

# PART B: Constitutional Entity Map

## B1. Owner Room

Responsibilities:

- constitutional leadership
- ratification
- strategic direction
- delegation review
- partnership governance
- quarterly review acceptance
- high-risk governance decisions
- cross-department conflict resolution
- registry/pipeline legitimacy
- AI policy governance

Must not:

- become super-admin
- execute daily operations
- mutate operational truth directly
- become finance executor
- become legal executor
- bypass protected memory
- replace departmental analysis with personal impulse

Owner Room doctrine:

```text
Owner ratifies legitimacy.
Owner does not become the cockpit.
```

## B2. Control Room

Sub-units:

- Monitoring
- Complaints & Disputes
- Analytics
- Reporting
- Support Continuity

Responsibilities:

- observe
- aggregate
- escalate
- report
- track anomalies
- track queue health
- create cases
- forward signals to departments
- monitor command/audit status in the future

Must not:

- become finance
- become legal
- become trust authority
- become owner authority
- mutate sovereign truth
- silently resolve high-risk disputes
- control tenant/clinician/client truth beyond scope

Control Room doctrine:

```text
Control sees the system.
Control does not own the system.
```

## B3. Technical Department

Responsibilities:

- development
- infrastructure
- deployment
- reliability
- security
- system evolution
- technical risk review
- implementation sequencing
- backup and continuity support
- future command/audit/runtime architecture

Must not:

- become hidden backend dictatorship
- ship authority changes without governance
- bypass Owner ratification for high-risk decisions
- encode policy secretly in code
- treat implementation convenience as constitutional authority

## B4. Trust & Verification

Responsibilities:

- center verification
- clinician verification
- document review
- license review
- appeal handling
- profile change review
- trust/blocking recommendations
- verification evidence preservation

Dual verification doctrine:

```text
System Review
+
Human Review
```

System Review may check completeness, consistency, expired documents, duplicate signals, and rule flags.

Human Review must judge context, legitimacy, appeals, exceptions, and consequences.

Trust & Verification must not remain generic admin approval forever.

## B5. Finance

Finance is split conceptually into two layers.

### Operational Finance

Responsibilities:

- payment evidence queue visibility
- payment status review support
- accounting backlog tracking
- payout delay tracking
- finance anomaly reporting
- reconciliation preparation

Operational Finance may prepare and analyze. It must not silently create final financial truth.

### Entity Finance

Responsibilities:

- payment approval/rejection authority
- payout readiness
- payout confirmation
- settlement
- refund authority
- accounting finality
- finance correction
- financial archive eligibility
- financial reconciliation

Entity Finance is sovereign-grade and requires protected memory before hard execution.

## B6. Legal + HR

Responsibilities:

- compliance
- contracts
- retention
- disputes
- legal holds
- legal risk review
- consent evidence policy
- staffing
- HR policies
- internal accountability
- legal archive review

Legal + HR must not become a universal veto room over ordinary operations. It acts where law, evidence, employment, compliance, retention, or dispute risk exists.

## B7. Marketing & Content

Responsibilities:

- content strategy
- publication
- library governance
- public communication
- brand voice
- ethical claim review
- content lifecycle review
- campaign governance
- coordination with Legal where claims are sensitive

Marketing & Content must not manipulate users emotionally or make unsupported mental-health claims.

## B8. Knowledge & Archive Office

Responsibilities:

- institutional memory
- governance packages
- constitutional history
- snapshots
- backups
- quarterly archives
- report aggregation
- migration wave archive
- extraction wave archive
- GitHub snapshot references
- backup manifests
- doctrine version tracking

Knowledge & Archive Office is not merely file storage. It is the continuity function of the institution.

Doctrine:

```text
If the institution cannot remember,
it cannot govern.
```

# PART C: Signal Flow Topology

## C1. General Signal Flow

```text
User
↓
System
↓
Control
↓
Department
↓
Owner
```

Signals do not automatically become decisions. Signals become cases, reports, or recommendations.

## C2. Signal Types

| Signal Type | Origin | Control Action | Department Action | Owner Action |
| ----------- | ------ | -------------- | ----------------- | ------------ |
| complaints | client/clinician/center/support | log, classify, escalate | analyze domain issue | ratify if high-risk/policy |
| disputes | users, finance, support, trust | preserve signal, escalate | legal/finance/trust analysis | ratify broad/high-risk action |
| verification requests | registration/profile changes | queue visibility | Trust & Verification review | ratify policy/appeal edge cases |
| operational anomalies | system/admin queues | monitor, report | Technical/Finance/Support analysis | prioritize if structural |
| policy concerns | staff/user/system | capture and forward | relevant department analysis | constitutional/policy decision |
| support continuity signals | support/chat/follow-up | observe and escalate | Support/Legal if consent-sensitive | ratify policy changes |
| finance anomalies | payment/payout/accounting | observe only, escalate | Finance analysis | ratify broad finance policy |
| legal concerns | disputes/compliance/archive | observe signal only | Legal analysis | ratify high-impact decision |

Signal law:

```text
A signal is not authority.
```

# PART D: Decision Flow Topology

## D1. Standard Decision Flow

```text
Signal
↓
Analysis
↓
Recommendation
↓
Ratification
↓
Execution
↓
Archive
```

## D2. Analysis Layers

### Human Analysis

Human analysis evaluates:

- context
- ethics
- operational reality
- user impact
- legal/finance/trust consequences
- exceptions
- proportionality
- humane boundaries

### AI Analysis

AI analysis may assist with:

- summarization
- pattern detection
- anomaly grouping
- risk hints
- report drafting
- comparison across cases

AI must not decide.

### Comparison Layer

The comparison layer checks:

- Does AI analysis conflict with human review?
- Does human review ignore data signals?
- Is the recommendation supported by evidence?
- Is the proposed action within constitutional limits?
- Does the action require Owner ratification?
- Does the action require protected memory?

## D3. Owner Ratification

Owner ratification applies when decisions are:

- constitutional
- strategic
- high-risk
- cross-departmental
- policy-changing
- finance/legal broad impact
- partnership-related
- authority boundary-changing
- emergency/post-emergency review

Owner ratification must not replace department analysis.

## D4. Execution

Execution may be:

- manual today
- delegated today
- technical implementation later
- command/backend execution in the future

Execution must follow ratified authority. It must not create hidden authority.

## D5. Archive

Every major decision flow produces memory:

- signal
- analysis
- recommendation
- ratification
- execution result
- follow-up
- review status

Archive is the bridge between governance and continuity.

# PART F: Archive Flow Topology

## F1. What Enters Archive

Archive receives:

- governance reports
- quarterly reviews
- constitutional amendments
- migration waves
- extraction waves
- sovereign waves
- audit reports
- GitHub snapshots
- backup manifests
- decision packages
- delegation records
- department activation records
- risk register updates
- freezer registry updates
- meeting outputs

## F2. Archive vs Protected Memory vs Operational Truth

| Layer | Meaning |
| ----- | ------- |
| Operational Truth | Active runtime state used by the system. |
| Protected Memory | Append-only or protected institutional memory of meaningful events. |
| Archive | Organized institutional records, reports, snapshots, packages, and history. |

Archive is broader than audit. Protected Memory is stricter than archive. Operational Truth is current state.

Example:

```text
Operational Truth: booking status is completed.
Protected Memory: who completed it, when, under what authority.
Archive: quarterly report describing completion trends and governance issues.
```

## F3. Archive Flow

```text
Signal / Report / Decision
↓
Department or Control package
↓
Knowledge & Archive Office
↓
Quarterly archive
↓
Owner review acceptance
↓
Constitutional history
```

# PART G: Delegation Flow Topology

## G1. Delegation Flow

```text
Department Missing
↓
Delegation
↓
Temporary Holder
↓
Review
↓
Department Activation
```

## G2. Delegation Lifecycle

Each delegation must define:

- missing department/function
- temporary holder
- scope
- limits
- authority exclusions
- review interval
- expiry or renewal condition
- activation target

## G3. Delegation Expiry

Delegation should expire or be reviewed when:

- department becomes operational
- risk increases
- authority expands
- quarterly review occurs
- conflict appears
- temporary holder becomes overloaded

## G4. Delegation Review

Delegation review asks:

- Is this still temporary?
- Has the holder exceeded scope?
- Is the future department ready?
- Has delegation become hidden authority transfer?
- Is documentation sufficient?

Delegation doctrine:

```text
Delegation != Authority Transfer
```

Today, Mental Smile should operate using:

```text
Owner
Development
Trust Function
Control Lite
```

without pretending mature departments already exist.

## I2. Owner

Owner currently carries:

- constitutional leadership
- priority decisions
- delegation decisions
- strategic judgment
- high-risk review

Owner must self-limit to avoid super-admin behavior.

## I3. Development

Development currently carries:

- code execution
- technical grounding
- documentation creation

Development must not become policy authority.

- clinician verification
- center verification

Control Lite should begin as:

- observation
- issue capture
- queue awareness
- escalation notes
- reporting
- anomaly forwarding

Control Lite should not become mutation authority.

## I6. Transitional Rule

```text
Operate with the team you have.
```

# PART J: Final Governance Blueprint Verdict

## J1. Constitutional State Structure

Mental Smile's constitutional state structure is:

```text
System produces signals.
Control gathers and escalates.
Departments analyze.
Owner ratifies.
Technical or future trusted execution acts.
Archive preserves.
Protected Memory proves.
```

## J2. How Information Moves

Information moves upward:

```text
User/System
-> Control
-> Department
-> Owner
-> Archive
```

Information should be filtered by scope and sensitivity, not dumped universally.

## J3. How Decisions Move

Decisions move through:

```text
Signal
-> Human + AI analysis
-> recommendation
-> ratification where required
-> execution
-> archive/protected memory
```

## J4. How Memory Moves

Memory moves into two forms:

- Protected Memory for events that must be defensible.
- Archive for institutional reports, packages, decisions, and continuity.

## J5. How Authority Moves

Authority moves downward only after legitimacy:

```text
Constitution
-> Owner ratification / Department authority
-> execution path
-> audit/archive
```

No room receives authority merely because it sees information.

## J6. How Delegation Moves

Delegation moves temporarily:

```text
Missing department
-> temporary holder
-> scoped responsibility
-> periodic review
-> future activation or renewal
```

Delegation is a bridge, not a throne.

Final doctrine:

```text
Mental Smile's governance topology is not a chart of power.
It is a circulation system:
signals rise,
decisions descend,
memory accumulates,
and authority remains bounded.
```
